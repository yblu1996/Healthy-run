### 评估：迁回境内 + 数据出境（用户第三问，仅评估未改代码）

产出《数据出境与迁回境内评估.md》（项目根目录）。核心结论：**不是"要不要迁"，是"什么时候迁"，且与"什么时候注册主体"是同一件事。**

**法律定性（核实条文，非推测）**：
- 出境事实成立：Supabase(境外) 存账号/诊断记录/跑步图片；仅智谱 GLM 在境内。
- **敏感个人信息无人数豁免**。《促进和规范数据跨境流动规定》第五条豁免第六项原文含括号"**不含敏感个人信息**"——1 个人也要合规。
- **本项目数据构成敏感个人信息，两项独立成立**：① 医疗健康信息——GB/T 45574-2025 注释说体重/身高/血压等"与疾病医疗无关则不属敏感"，**但浩天律所明确：一旦经算法形成"疾病诊断/健康评估/医疗建议性质"的输出，即按医疗健康信息对待**。跑悟输出诊断+损伤预警+运动处方，正落此条。② 步态信息=生物识别敏感信息（GB/T 41773）。
- **三条出境路径在本场景实操全堵死**：卡点不在中方，在**境外接收方不配合**——标准合同须用网信办范本、要求境外方接受中国管辖+配合监管，Supabase 不可能签；认证同理。
- 2026 新变化：新版《网络安全法》2026-01-01 施行（**取消"初次违法仅警告"容错**）；《个人信息出境认证办法》2026-01-01 施行；《网络数据安全风险评估办法》2026-08-20 施行。

**连带成本（真正的代价）**：迁回境内 ⇒ 必须 ICP 备案 ⇒ 撞《互联网信息服务管理办法》第 3/4/7 条：**个人备案不得经营性，收费需 ICP 经营许可证（须内资公司，个人/个体户拿不下）**。若做微信小程序，个人主体另有三堵墙：**开不了支付商户号 / 不支持 web-view 业务域名（H5 不能复用）/ 医疗类目禁选**，且**主体类型选定后不可变更，试水选个人就是不可逆错误**。

**选型推荐**：轻量服务器 + 自建 PostgreSQL + COS。自托管 Supabase 虽代码改动最小但 10+ 容器运维太重；WorkBuddy 内置云服务以"前端+publishableKey+Origin"为中心、不提供 service-role 给自建后端 → **与本项目"后端持全部密钥"的架构冲突，不推荐**。
**Dify 去处**要一并决定（一起上云需 4C8G／留本机需穿透／拆掉直连智谱但失去可视化调参）。

## 核实「一键启动前是否需要先跑一键停止」+ 审查一键停止.bat（11:56）

**结论 1**：一键启动是幂等的（逐服务健康检查，健康即 skip），**平常不需要先停止**。
唯一需要先停止的场景：某服务**已健康在跑但希望它重启**（如跑悟要加载新后端代码，否则被 skip 掉继续跑旧代码）。

**结论 2**：一键停止.bat 可用，当前不会出故障，但发现 1 条真实隐患 + 若干小瑕疵：
- ⚠️ 隐患：**不清理 pm2**。若 pm2 daemon 在跑且管着 health-app/as-naming，`taskkill /F` 后 pm2 的
  autorestart 会把进程再拉起来 → 停止不彻底。启动侧第 0 步有 `pm2 delete/save/kill` 防护，停止侧没有。
- ⚠️ 文案不符：标题 "Stopping all services" 但**不停 Openclaw(18789)**（停不停是有意选择，文案易误解）。
- 小瑕疵：无 `setlocal`；`:killport` 覆盖式赋值（同端口多行只留最后 PID，实测 IPv4/IPv6 同 PID 故安全）；
  `docker compose stop` 失败只报 WARNING 不说明容器实际状态；`taskkill /F` 强杀（可接受）。

**实测的 pm2 现状（好消息）**：`pm2 jlist` 为空 —— daemon 里没有任何应用，3000(PID 13368)/3210(PID 16056)
是 `run-hidden.vbs` 直接拉起的 node，**不是 pm2 管的** → 此刻跑一键停止安全，不会"停了又起来"。
`~/.pm2/dump.pm2`（9-21 存档）里仍登记 health-app/as-naming，但只有执行 `pm2 resurrect` 才会发作。
> 为查此状态启停过一次 pm2 daemon（任意 pm2 命令都会顺带 spawn 一个空 daemon），已 `pm2 kill` 收尾，
> 端口 3000/3210/18789 全程未受影响。`wsl.exe` / `wmic.exe` 均被安全策略拉黑，无法执行。

**给用户的最优路径**：直接「一键停止.bat → 一键启动.bat」一步同时解决 Dify 修复 + 跑悟换新代码
（停止里 `docker compose stop` 会因 daemon 挂掉而失败，但容器本就是 Exited，不影响后续 `up -d`）。

## 一键启动窗口自动关闭的根因：我编辑 .bat 时踩了 cmd 的块内括号坑（12:17）

用户报："一键启动窗口自动关闭，不像以前按任意键，结果两个程序也没启动。"

**三条独立证据**指向同一个结论：

1. `WorkBuddy/logs/paowu.log` 时间戳还是 9-23 19:48、`naming.log` 还是 9-22 13:08 → 批处理
   **根本没走到启动这两个程序的步骤**（不是"启动了但失败"，失败也会写日志）。
2. 用户贴的 compose 输出停在 `dify-runtime-up.sh` 第 5 步中间，之后应打印的
   `[Dify] waiting for :8180, up to 240s ...` 从未出现 → 中止点在脚本返回之后。
3. `diff 一键启动.bat.bak-20260924-difyfix 一键启动.bat` 显示，我 11:51 那次编辑在
   `if errorlevel 1 ( ... )` 块**内部**新写了两行 `echo          1) wsl --shutdown` 和
   `echo          2) 一键启动.bat   (it restarts Openclaw + Dify together)`。

**根因**：cmd 的块扫描按字节数括号深度，`1)` 里的 `)` 直接把块**提前闭合**，剩余文本变成语法垃圾
→ 致命解析错误 → 批处理当场中止。cmd 是**逐条语句解析**的，而这条 `if errorlevel 1 (...)` 语句
恰好紧跟在长时间运行的 `wsl ... dify-runtime-up.sh` 之后才被解析 —— 所以窗口就在那一刻关闭，
跑悟/起名再也没被拉起。原文件那几行 echo 里没有圆括号，所以"以前正常"。

**修复**：把那两行改成 `1. wsl --shutdown` / `2. 一键启动.bat  -  restarts Openclaw and Dify together`
（块内不用圆括号，比转义更不容易再踩）。备份 `一键启动.bat.bak-20260924-difyfix` 里的写法可作为对照。

**验证手段（cmd.exe 被沙箱禁用，无法实测，改用静态检查）**：写了个 Node 小脚本按行跟踪括号深度
（注意 `) else (` 是"闭合+开启"、净深度不变，第一版没处理导致误报 13 处），再检查深度>0 时
`echo`/`rem` 参数里的未转义 `(`/`)`。修正后 `一键启动.bat` 与 `一键停止.bat` 均为 **括号平衡、0 问题**。

**教训**：改 `.bat` 后必须做这个静态检查（cmd 的解析错误会让窗口静默关闭，极其难查）；
诊断"程序没启动"优先看目标程序的日志**时间戳**，能立刻区分"没走到"与"走到但失败"。
