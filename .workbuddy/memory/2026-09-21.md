### 本机三大坑（都踩过，都在启动器里规避了）
1. **curl 必须加 `--noproxy "*"`**：本机有系统代理，裸 curl 探测 localhost 会走代理，目标 down 时代理回 502 体但 **curl 退出码仍是 0**，探测逻辑完全失真（曾因此误判服务在运行）。
2. **bat 文件必须存 GBK(936) 不能存 UTF-8**：中文系统 cmd 按代码页 936 解析 bat，UTF-8 的中文字节会破坏 cmd 的括号块解析，表现为整个 bat 静默不执行。
3. **不要在 bat 里用 findstr 匹配中文**：Express 的 res.json 输出 UTF-8，findstr 的模式来自 GBK 的 bat，字节不一致永远匹配不上。起名测名的识别改为「3210/8080/8888/4321 上 /api/health 能通即它」（跑悟固定占 3000），纯 ASCII 判定。

### 沙箱限制（以后排查要知道）
- PowerShell 工具里 `Start-Process cmd.exe` / 直接跑 `.bat` 被安全策略拦截；Bash 工具的 `cmd.exe //c` 会被 git-bash 路径转换搞成交互模式（实际没执行命令，banner+提示符是特征）——**本沙箱无法执行 cmd/bat**，bat 只能靠逻辑审查 + GBK roundtrip 校验。
- Write 工具**覆盖 GBK 编码的文件时会把中文写成 `?`**（v1 被 '?' 覆盖过）。正确做法：Write 到一个新的 ASCII 文件名（UTF-8），再用内联 PowerShell `[IO.File]::ReadAllText(src,UTF8)` + `WriteAllBytes(dst, GBK)` 转换。
- **PS 5.1 把 Write 工具生成的 .ps1 按 ANSI(936) 读**，里面的中文字符串会变乱码（字符串长度都会变）。含中文的逻辑必须用 PowerShell 工具的**内联命令**（内联中文正常），或 .ps1 里只用 ASCII。

## 分析超时真凶（SSE 探测定案）

用户反馈"分析失败、服务器延时过长"，怀疑模型/额度。实测排除：`dev-tests/dify-sse-probe.js` 订阅 Dify SSE 事件流打时间戳，10 张图全链路：

- 开始节点 0s；**识图节点 63.3s**；**诊断计划节点 479.9s**；结束 0.1s。总 543.3s，status=succeeded，32894 tokens。
- 结论：**模型可用、额度充足**。慢在诊断计划节点（GLM-5.3-Flash 的 reasoning + 逐周生成 8 周计划），单节点近 8 分钟。
- 三处超时线都短于 543s，全部会误杀：后端 `lib/dify.js` 总超时 470s、僵尸清理 8 分钟、**前端 /diagnose fetch 超时 300s（最先放弃的就是它）**。

修复（全部对齐实测）：

- `lib/dify.js`：废弃固定总超时，改**空闲超时 + 硬上限**——每个 SSE 事件续期 180s，只有 3 分钟无任何数据才判卡死；15 分钟绝对兜底。abort 转可读文案（旧代码读流期的 AbortError 直接冒泡，用户只看到"操作被中止"）。常量支持 env 覆盖（`DIFY_IDLE_TIMEOUT_MS`/`DIFY_HARD_TIMEOUT_MS`，默认值即生产值，仅供测试注入）。
- `api/index.js`：`cleanStalePending` 僵尸线 8 分钟→12 分钟（小于 Dify 硬上限，避免还在跑的记录被历史页误标失败）。
- `public/app.js`：`/diagnose` 前端超时 300s→960s（必须大于后端，否则服务器还没放弃前端先放弃，用户拿不到准确原因）；步骤节奏 `[0,40s,90s,150s]`→`[0,70s,200s]` 对齐实测（识图 63s、诊断 480s），420s 提示改"正在逐周生成 8 周训练计划…约 5-10 分钟"。
- `public/index.html`：loading-sub "2-5 分钟"→"5-10 分钟"；loading-note 说明第 4 步本身就是最慢的一段。
