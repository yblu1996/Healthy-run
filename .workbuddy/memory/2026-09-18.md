### 查库轨迹（一缕春风 18853339895）
| 时间(北京) | version | 状态 | 目标 |
|---|---|---|---|
| 9/17 22:59 | v7 | done | 半马（最早） |

| 9/18 09:08 | v3 | done | 全马 |
| 9/18 09:13 | v4 | done | 全马（最新） |

- 根因 1（序号乱）：用户删 6 条记录时服务还是旧代码（无重编号），v7 保留原编号没变 v1。之后新提交用 `version = count+1`，当时只剩 1 条 → 从 v2 起递增，与 v7 错位成 7/2/3/4，缺的 1/5/6 压根不存在。
- 根因 2（主页不同步）：GET /records 按 version desc 排序 → done[0] 永远是 v7（半马、旧 8 周计划）。而"已诊断 N 次"用 done.length，所以只有数字同步、目标/计划不换，造成"同步了第 2 次但目标还是半马"的现象。

### 修复
1. 版本号分配改 `max(version)+1`（不再是 count+1）：新记录编号永远递增，删除造成的空位不再污染新编号。
2. GET /records 排序改 `created_at desc`：主页 done[0] = 真实时间最新的那条；历史页也是最新在上。
3. 存量整理：两轮占位法把该用户记录按时间重排成 v1(半马)/v2(失败)/v3/v4(全马)，连续整齐。

- **选型：方案 1**。理由：识图目的是"综合多张截图出一份指标"，一次调用看全图比逐张循环更快更省；方案 2 要加循环+聚合节点，识图输出从对象变数组，节点 2 和后端解析都得跟着改，验证期不划算。对比表已写进设计文档第九节。
- **后端已改**（lib/coze.js）：新增 `buildImageParams`，把 images 数组拆成 image1..imageN（≤10），过滤空串、非数组兜底、不补空位；旧 `images` 字段保留兼容。api/index.js 在【填报数据】块追加"本次实际上传图片张数：N"，让模型知道有几张图可看，约束空位臆造。
- 逻辑单测全过：3 张→image1/2/3；空串被过滤；13 张截断到 10；非数组返回空对象。
- 空位风险兜底：扣子开始节点 image1~image10 全设非必填 + 提示词加"未提供的图片忽略"。**若空参数让工作流报错，切方案 2**，改动集中在 buildImageParams 一处（改输出 image_list 数组）。
- 文档更新：第二节参数表加 image1~image10；第九节重写多图说明（选型对比表 + 操作清单 6 步 + 验证标准）。
